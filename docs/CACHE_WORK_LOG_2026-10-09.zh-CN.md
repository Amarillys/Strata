# 从前缀重填充到 512K 会话池：2026-10-09 工作记录

本次解决的是主会话被插入请求打断后反复处理长历史的问题。先启用了跨会话 RAM 缓存，
验证了检查点间隔的作用，随后按用户最终选择实现并部署了 **512K 总 token、三个有 ID 通道
加一个共享无 ID 通道**。单会话上限为 307200 token，推理仍为串行。

65K 主会话插入约 10K 子任务后，返回主会话实测只补读 20 token，脚本耗时 0.907 秒。
这验证了完整会话状态的保留与恢复；新会话的首次 prefill、缓存淘汰和输入改写仍有各自的代价。
本记录描述截至本次部署的结果；后续实际设置以运行配置、引擎 `INFO` 和 `/metrics` 为准。

## 1. 最初为什么重新 prefill

原先 `--conversation-cache-mib` 为 0，跨会话完整状态停放没有开启。`--prompt-cache 6`
只保存当前历史分支的恢复检查点。短请求覆盖活动 KV 工作区后，长历史的不兼容检查点失效，
返回长会话便需要重新读取。

当时的生产日志记录如下，原始分析保存在
[模型切换记录](IQ_KT_MODEL_SWITCH.zh-CN.md)的“2026-10-09：一次短请求导致长对话重新 prefill”一节。
该旧文档其他段落中的“当前配置”属于早期状态，不代表最终的 512K 配置。

| 请求 | 输入 token | 复用 token | 新读入 token | Prefill 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 长会话 | 27,645 | 26,867 | 778 | 3.942 s |
| 插入短请求 | 284 | 0 | 284 | 2.396 s |
| 返回长会话 | 29,051 | 0 | 29,051 | 41.569 s |
| 下一轮续聊 | 29,247 | 29,046 | 201 | 2.224 s |

这些请求发生在同一引擎进程内。检查点没有按分钟设置的过期计时，GPU 唤醒模块的空闲计时
也不清除会话缓存。增大推理并行数只改变请求执行方式；要可靠保留主会话和子任务，还需要
独立状态、稳定的通道归属以及足够的缓存预算。

## 2. 相同客户端、相似前缀为什么仍会重读

另一次插入请求有 9,788 个输入 token，复用为 0，prefill 为 18.428 秒；随后主会话
66,436 个输入 token 复用了 66,405 个，快照恢复耗时 140.5 ms。用户确认插入请求来自
同一客户端的另一个会话或子任务，因此它的冷启动不等于主会话缓存也丢失。

复用需要最终渲染后的 token 前缀一致。系统提示、工具定义、模板、思考设置和图片都可能
改变前缀；“来自同一客户端”本身不足以证明一致。当时日志中的疑似 system 边界约为
7,933 与 7,689 token，提示输入结构可能不同，但请求录制未开启，不能定位具体哪个字段改变。
旧日志也无法追溯这些真实请求是否带有会话 ID。

该模型除 KV 外还有 GDN 循环状态。即使两个请求前面确实共享一段 token，长会话末尾的
循环状态也不能直接倒退到公共前缀结尾：需要那个位置的有效恢复状态，否则要从较早的
可用状态重新计算。最终会话池按 ID 隔离并保留完整状态，新 ID 的首轮仍会 prefill。

## 3. 期间完成的调整与验证

### 开启多会话缓存并扩展单会话上限

先启用了 `--conversation-cache-mib 8192 --conversation-cache-slots 4`，并将单会话上限
从 262144 调到 307200，配合 `--rope-scaling yarn --rope-scale 1.171875`。

63,032-token 长请求首次耗时 72.255 秒；插入短请求后，返回长会话的 63,055 个输入 token
复用了 63,035 个，只补读 20 个，耗时 0.793 秒。该测试证实 RAM 停放能解决整段长历史
被短请求覆盖后的重读；没有验证完整 300K 长度的模型质量。

证据：本机 `logs/cache-300k-20261009-ciy1wnzq/probe.json` 和 `probe.engine.log`。

### 将周期检查点间隔调为 4096

按用户要求，曾将周期检查点间隔从默认 16384 调到 4096，数量仍为 6。
小规模对照中，A 首次输入 6,857 token；系统提示尾部不同的 B 输入 6,918 token，
复用了 4,096 个、补读 2,822 个，耗时 6.239 秒。返回 A 时输入 6,879 token，
复用 6,859 个、补读 20 个，耗时 0.640 秒。

这个结果说明更密的检查点能提供更细的恢复位置。代价是更频繁的状态复制和管理：旧实现
每份检查点典型约 118 MB，主要包含循环状态、索引尾部及历史，KV 本身另存。
只保留六份时，缩短间隔会让历史恢复位置更快轮换。

**六个检查点既不是最多容纳 6 × 4096 token，也不是六份独立会话。** 它们表示处理到某些
位置时的恢复状态。源码显示旧淘汰策略保护的是最早检查点；4096 间隔下，受保护的可能是
4096 位置，约 8K 的 system 末尾不一定被永久保留。因此，65K 长会话之后插入约 10K 请求，
六个检查点无法保证覆盖所需的公共前缀边界。

上述小测试没有覆盖 65K 时的检查点淘汰。原计划的旧策略 65K 保留实验在用户改选会话池后
没有继续，`logs/checkpoint-retention-65k-20261009-m7mmnekf/` 只有基线记录。
4096 实测证据位于 `logs/checkpoint-4096-20261009-zeo4ja4k/`。

## 4. 最终实现：512K、3+1 会话池

用户先提出 1M，随后明确缩为 512K，并要求没有 ID 的请求共用一个通道。最终在现有 host
会话快照机制上增加了按身份路由、总 token 预算和淘汰管理。功能由新参数显式开启，
没有把它设为全项目默认行为。实现与接口说明见 [CONVERSATION_POOL.zh-CN.md](CONVERSATION_POOL.zh-CN.md)。

| 配置 | 最终值 | 含义 |
| --- | --- | --- |
| `--conversation-pool-tokens` | `524288` | 512 × 1024 个逻辑 token，包含活动会话 |
| `--conversation-cache-slots` | `4` | 三个有 ID 会话和一个共享无 ID 通道 |
| `--conversation-cache-mib` | `12288` | 12 GiB 快照字节预算，按需分配 |
| `--conversation-cache-min-free-mib` | 默认 `2560` | 保存/恢复快照时的物理可用内存门槛 |
| `--max-context` | `307200` | 单会话上限，独立于池的总量 |
| RoPE | `yarn` / `1.171875` | 扩展原生 262144 上限 |
| KV / GPU 常驻量 | `int8` / `20480` | 实际为 K8V8，完整状态可驻留 RAM |
| `--prompt-cache` / `--prompt-cache-every` | `2` / `0` | 关闭周期检查点，至多保留根与最近轮次恢复状态 |
| Prefill / layer split | `2048` / `22` | 保留本机预设设置 |
| 推理并行 | 串行 | 四个缓存通道不表示四条请求同时推理 |

每个通道保存最新完整 KV 和运行状态。总 token 按真实提示和已生成内容增长，不预占请求的
`max_output_tokens`。第四个新的有 ID 会话淘汰最久未使用的有 ID 会话；超出 token 总量时
淘汰其他通道的整份上下文。匿名名额独立保留，但匿名内容同样受总容量和物理内存限制。
字节预算或 RAM 紧张时，可能在到达 512K 前淘汰或跳过保存。

路由支持显式 `strata_conversation_id` / `conversation_id`、body/metadata/client_metadata
中的 session/thread、相应请求头、Codex turn metadata 及 Claude 内嵌 session。
主会话与子任务按 `session_id + thread_id` 区分。每次变化的 `request_id`、普通用户 ID 和
可能共享的 `prompt_cache_key` 不作为会话身份。没有有效 ID 的请求全部进入同一个匿名通道。

ID 只决定归属，不跳过 token、图片和控制状态的匹配。同 ID 改写早期历史会替换旧分支；
新会话首轮、被淘汰后返回、重启后返回都可能重新 prefill。日志仅输出身份来源和散列，
`/metrics.conversation_pool` 给出总额度、通道占用和淘汰信息。

主要代码变化：

- `include/strata/program/conversation_pool.hpp`：新增通道分配、总量和 LRU 淘汰策略。
- `include/strata/core/conversation_cache.hpp`：快照归属、按身份匹配、替换与移除。
- `src/program/generate.cpp`：参数、身份协议、完整状态切换、生成增长检查和 POOL 指标。
- `serve/conversation_pool.py`、`serve/server.py`：身份识别及 Chat Completions、Responses、
  Messages 三条 API 路径传递。
- `src/core/conversation_cache_test.cpp`、`serve/test_conversation_pool.py`：策略与 API 回归测试。

## 5. 内存、显存与硬盘的边界

本实现已经使用系统 RAM 保存完整 KV/会话状态，GPU 只保留部分常驻工作集。显存还有空闲，
不等于任意增大上下文没有代价；索引、循环状态、模型权重和工作缓冲也需要空间，两块卡的
空闲显存不能直接合并为一个统一池。

按本模型当前 INT8 KV 布局估算，每 token 约 12,672 字节。512 × 1024 token 的 KV 本体
约 **6.1875 GiB**，还需要循环状态、检查点、索引及切换缓冲，所以设置了更大的 12 GiB
快照预算。这是布局估算，不是把 512K 填满后的实测内存峰值。

若“10M”指一千万 token，仅 KV 就约 **118 GiB**，已超过本机约 64 GiB 系统内存。
硬盘能保存数据，但读写和恢复有耗时；磁盘容量不会自动扩展单会话上限、模型有效上下文
或循环状态的回退能力。本次没有实现磁盘缓存池，当前池模式不支持 SAVE/RESTORE，
双 GPU 的会话文件路径也不能作为现成替代。池在进程重启后清空。

## 6. 部署与实测

本机为 Windows / CUDA，RTX 2080 Ti 22 GiB + RTX 4080 SUPER 32 GiB，系统 RAM 约 64 GiB，
Intel Iris Xe 负责视觉编码。模型为 `qwen3.8-flash-next-v4-iq3kt`，层 0–21 / 22–47 分置两卡。
`--spec 3` 是验证窗口设置；没有启用 `--mtp`，没有加载草稿模型。

部署配置：`strata-iq3kt-v4-dual22-k8v4-pf2048-vision-igpu.json`。
文件名保留 `k8v4` 历史字样，实际 KV 为 `int8`。运行的是基于 0.1.41 的本地构建
`build-kt/pool-candidate/strata.exe`，原 `build-kt/Release/strata.exe` 保留作回退。
配置、实际 exe、启动参数和二进制哈希均记录在本机验证目录，不在本记录中固定 PID。

长 A 与短 B 使用相同系统提示、同一 session 下不同 thread；温度 0、top_k 1、关闭思考，
输出为短回复。以下为脚本耗时，包含一次 `/metrics` 读取，不是单独的 prefill 耗时。

| 场景 | 输入 token | 复用 token | 补读 token | 耗时 |
| --- | ---: | ---: | ---: | ---: |
| A 首次长请求 | 65,026 | 0 | 65,026 | 71.132 s |
| B 首次子任务 | 9,677 | 0 | 9,677 | 14.623 s |
| 返回 A | 65,048 | 65,028 | 20 | 0.907 s |
| 匿名通道被替换后返回 A | 65,073 | 65,051 | 22 | 0.739 s |
| 第四个有 ID 会话进入后返回 A | 65,101 | 65,078 | 23 | 0.880 s |
| 被淘汰的 B 再次进入 | 9,699 | 0 | 9,699 | 14.304 s |

第四个有 ID 会话淘汰的是当时最久未使用的 B，最近访问的 A 和匿名通道得以保留。
共 12 次请求，运行断言均通过；两条短贪心请求的 API 回复与旧构建一致，这不代表全局逐位等价。
测试结束时池占用 82,714 / 524,288 token，host cache 统计 2,637,418,112 字节，服务健康且空闲。
这些是测试结束时的快照，不代表此后一直保持相同占用。

证据目录为 `logs/conversation-pool-512k-20261009-x0_h3icj/`：

- `RESULTS.md`、`candidate.json`、`candidate.engine.log`、`probe.py`：过程与运行结果。
- `baseline.json`：旧构建的两条短贪心回复对照。
- `after-start.json`、`final-state.json`：启动与收尾状态、二进制及源码哈希。
- `restart.py`：当次等待请求完成、验证启动、失败回退的部署脚本。

该目录位于本机日志区，不作为公开交付包；其中 `config.before.json`、`config.candidate.json`
含凭据，不应整份打印或提交。源码与文档中的去敏结论可以供后续维护查阅。
