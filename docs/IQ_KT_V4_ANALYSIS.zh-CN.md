# v4 IQ3_KT：显存、性能与后续优化

2026-10-08，Windows、i9-12900HK、64 GiB RAM、2080 Ti 22 GiB、4080 SUPER 32 GiB。
早期基准使用合入上游 0.1.40.3 后的本地 KT 版本，最后新增 0.1.41 的 256K 分层实验。
本文复核 GGUF 张量、加载器、容量与实测；未运行的优化保留为候选。服务使用已验证的 v4 预设，
启动和切回 v2 的方法见 [按需启动](IQ_KT_MODEL_SWITCH.zh-CN.md)。

**仍有优化空间。** 当前问题是 v4 越过了原有的全驻留预算，2080 阶段重新需要 CPU 专家和
RAM→GPU 流送，并恢复了逐层 host 协调。优先优化这些额外开销，比继续压缩 KV 更有针对性。
不过，保持当前权重、上下文和运行时的前提下，尚无已验证的设置能恢复 v2 约 60 tok/s。

当前采用 **0.1.41、22＋26、256K、K8V8、预留 1,024 / 128 MiB、前缀缓存 6**。
4080 的 26 层专家全部驻留，两卡共 22,402 个专家，RAM 专家 **4.11 GiB**。
短/中输入平均 **41.43 / 41.86 tok/s**，比同版本 21＋27 / 200K 慢约 **1.4–2.0 tok/s**；
实际 261,618-token 输入后生成 384 token 为 **36.6 tok/s**，检索和立即续聊缓存均通过。
按用户对容量的偏好采用该方案。下面保留历史 200K 调优和新版 256K 实验各自的测量条件。

## 增大的究竟是哪部分

`IQ3_KT` 是混合量化方案的名称，不表示每个张量都是 IQ3_KT。

| 内容 | v2 | v4 | 变化 |
| --- | ---: | ---: | ---: |
| Routed experts | 44.41 GiB | 47.15 GiB | +2.73 GiB |
| 两阶段的其他 GPU 权重及输出头 | 3.43 GiB | 5.03 GiB | +1.60 GiB |
| 全驻留所需 GPU 权重载荷 | 47.84 GiB | 52.18 GiB | **+4.34 GiB** |
| PLE 大表，当前位于 SSD | 25.03 GiB | 20.27 GiB | −4.77 GiB |

表中按实际 v2 split 19、v4 split 22 的裁剪规则计算，不含 CUDA、状态、工作区和分配器开销。
固定同一个 split 19 对比时，v4 其他权重为 5.04 GiB、增加 1.61 GiB；小差别来自阶段裁剪。
两套 GGUF 总文件大小几乎相同，约 72.52 GiB，差约 1.61 MiB。PLE 缩小抵消了磁盘文件的增量，
但不能抵消专家和稠密权重的显存增量。

具体变化是：

- 第 0–5、38–47 层，共 16 层的专家 gate/up 从 IQ3_KT 提高为 IQ4_KT；专家 down 仍为 IQ3_KT。
- 许多 attention、GDN 和 shared-expert 投影提高为 Q8_0，输出头由 Q6_K 改为 Q8_0。
- PLE 表从 IQ4_KT 改为 IQ3_KT。当前仍用 SSD `direct` 和行缓存，不把整张表载入 RAM。

这说明精度预算发生了重新分配，不能只凭版本号或更大的 GPU 权重断言所有能力都提高。

## KLD 下降主要来自什么

随后核对了[作者的发布说明](https://huggingface.co/ji-farthing/Qwen3.8-Flash-Next-Uncensored-ik-llama-GGUF/blob/85da41d98c3866c8cc75149287632c6e1be6c5e4/README.md)。
发布说明将这些文件列为同一 Uncensored 源模型的不同量化版本，没有报告 v4 重新训练。
两份本地文件也都记录 `qwen4exp-agentic-v3.imatrix`、`calibration-qwen4exp-v3.txt`、818 个条目、
2800 个 chunks；imatrix 路径一个是绝对路径，一个仅为文件名。元数据相同不等于校准文件的哈希验证，
但与作者“使用同一 imatrix”的说明一致。

作者报告的 IQ3_KT 对照如下，参考为 Uncensored BF16：

| 测试 | v2 mean KLD | v4 mean KLD | 降幅 | 与 BF16 的 top-1 一致率，v2 → v4 |
| --- | ---: | ---: | ---: | ---: |
| 英文 | 0.148445 | 0.085521 | 42.4% | 85.855% → 89.677% |
| 代码 | 0.140019 | 0.081702 | 41.7% | 92.551% → 94.350% |

现有证据支持：主要收益来自更合适的混合精度分配，尤其是提高经常参与计算的稠密部分的精度。
它不是所有权重统一加 bit：PLE 反而从 IQ4_KT 降到 IQ3_KT，整个文件大小基本不变。
也不能仅凭这个对照，把约 42% 的下降分别归因到专家、attention、SSM 或 HC。

一个更有针对性的旁证是作者的 **v3 IQ4_KT → v4 IQ4_KT**：作者明确说 routed experts 和 PLE
逐字节相同，英文/代码 KLD 仍由 0.132732/0.126022 降到 0.056010/0.057125，约降低 58%/55%。
说明大幅改善不需要以“专家继续加 bit”为前提，其他张量提高精度很重要。
这仍不是每类稠密张量的独立消融，也不能把它的百分比拆给 v2 → v4 IQ3_KT。

本地还抽查了保持同类型的 112 个 IQ3_KT 专家张量和 25 个 Q8_0 embedding/K/V 张量：
每个张量取五段、每段最多 4096 字节，两版样本全部一致。此检查支持“许多原格式权重未变”，
不证明全部张量相同，也不量化各项改动的质量贡献。作者说明 v4 使用 `d9e2868` 的 CUDA 量化器；
未做固定精度分配、固定量化器的消融，不能严谨地断言 KLD 的每一点变化都只由 bit 数决定。

**KLD 降低约 42% 不等于任务能力提高约 42%。** 它表示测试语料上的输出概率分布更接近 BF16。
作者只测了英文和代码各十个 2048-token chunk；该长度没有实际考验 DSA indexer 的长上下文筛选，
作者也明确说 indexer 使用 BF16 没有得到这个测试的验证。因此这组数据不是中文、工具调用、
复杂推理或 200K 长上下文的质量结论，也不是本机 Strata 部署的本地 KLD 实测。

若后续做节省显存的自定义版本，保留稠密部分 Q8、单独改变部分专家位宽，是值得先做的消融方向；
直接把稠密部分全降回旧精度，可能丢掉这次改善的重要来源。哪一组能保留多少收益仍需测量。

## 初始显存布局与性能（K8V4）

v4 使用 200K（204,800）容量、K8V4、20,480 resident cells、2048 prefill、MTP 关闭、
split 22，显存预留 1536 / 768 MiB。含核显视觉的实际启动布局：

| 阶段 | 层数 | 常驻专家 | 专家显存 | RAM 中的专家 |
| --- | ---: | ---: | ---: | ---: |
| 2080 Ti | 22 | 8,863 / 11,264 | 16.84 GiB | 2,401 个，4.54 GiB |
| 4080 SUPER | 26 | 13,312 / 13,312 | 25.77 GiB | 0 |

纯文本基准的 2080 缓存为 8,865 个；视觉位置表等分配使在线配置少了两个。
按初始 profile 复算，2080 各层驻留 350–458 个专家，22 层中没有一层的 512 个专家全部驻留。
4080 则进入全驻留的 CUDA graph 路径，省去专家部分的逐层 host 协调。
未驻留的 4.54 GiB 是权重集合大小，不是每个 token 都搬运 4.54 GiB，也不是访问未命中率。

已有同引擎、相同提示词、200K/K8V4/2048、MTP 和前缀缓存关闭的结果如下。短/中输入各两次、每次输出
256 token；204K 输入测试一次、输出 384 token。模型权重和分层点不同。

| 测试 | v2 split 19 | v4 split 22，自动流送比例 |
| --- | ---: | ---: |
| 3,570 输入后的 decode | 60.46 tok/s | 34.27 tok/s |
| 12,150 输入后的 decode | 62.17 tok/s | 34.81 tok/s |
| 204,000 输入后的 decode | 52.15 tok/s | 31.36 tok/s |
| 204,000 输入的 prefill | 190.27 s | 251.90 s |

两版均取回长输入中 20%、50%、85% 位置的三个校验串；这不是综合质量评测。

同一次 v4 加载中又做了流送比例补测：3,570 输入、256 输出，每个比例两轮。

| 未命中专家的 GPU 计算比例 | Decode | CPU 专家执行 | 等 GPU 到达逐层服务点 |
| --- | ---: | ---: | ---: |
| 自动，2080 约 0.17 | 34.12 tok/s | 9.45 ms/token | 10.79 ms/token |
| **0.5，当前预设** | **38.09 tok/s** | **6.25 ms/token** | **11.46 ms/token** |
| 1.0 | 31.89 tok/s | 0 | 22.30 ms/token |

0.5 比本组自动值快约 11.6%，因此已经采用。它只是在这三个候选中最快，尚未细扫，
这一阶段没有用 0.5 重测 204K 长输入；后面的 K8V8 测试才使用 0.5。
38.09 tok/s 不能直接当作满上下文速度。

这里的 GPU 等待来自 host 计时，包含 GPU 在到达服务点前执行的计算、访存和调度，
**不能当成纯 PCIe 传输耗时**，也不是全模型 GPU 算子时间分解。CPU 工作还会与 GPU 工作重叠。
现有数据支持“CPU 与 GPU 分担未命中比全部交给 GPU 更快”；尚不能逐项归因 v2→v4 的全部差距。
两张卡的有效 H2D 探测分别约 6.3 / 2.9 GB/s，不能把 2080 也按 USB4 处理。

## 中间方案：前缀缓存、K8V8 和 22＋26 层

先恢复两个日常预设的 `--prompt-cache 6`，再按用户要求将 v4 改为 `--kv int8`（K8V8），
把 2080 的 `--vram-reserve-mib` 从 1,536 降至 1,024；4080 仍预留 768 MiB。
上下文 204,800、resident cells 20,480、split 22、2048 prefill 和 `--pcie-frac 0.5` 保持。

| 项目 | 初始 K8V4 / 1,536 MiB 预留 | 中间 K8V8 / 1,024 MiB 预留 |
| --- | ---: | ---: |
| 2080 常驻专家 | 8,863 | **9,114** |
| 4080 常驻专家 | 13,312，全部 | 13,312，全部 |
| GPU 专家缓存合计 | 43,632 MiB | 44,117 MiB |
| RAM 专家 | 2,401 个，4.54 GiB | 2,150 个，4.07 GiB |
| 引擎完成加载后的 2080 空闲 | 1,328 MiB | 818 MiB |

此次多驻留 251 个专家、约 485 MiB，仍未达到整个模型专家全驻留。
K8V8 相比 K8V4 的 GPU resident KV 池多 56.25 MiB，200K 的完整 RAM KV 池多 562.5 MiB；
这部分 RAM 增量大致被减少的 RAM 专家抵消。K8V8 保留更高的 V 存储精度，
这里没有重做任务质量或 KLD 对照。

这一设置的 3,305-token 合成输入生成 256 token 为 39.5 tok/s，重复请求为 40.6 tok/s。
重复请求复用 3,298 token，仅新读入 7 个，prefill 为 0.106 s。
请求期间遥测最低空闲约为 2080 的 1,171 MiB、4080 的 1,580 MiB；遥测和引擎的
`cudaMemGetInfo` 不是同一内存口径，新增专家是否装得下需要实际分配和运行验证。
本轮没有取得同条件旧配置基线，不能把这些数字当成增加专家或 K8V8 各自的收益。

随后同一配置完成 204,018-token 输入，prefill 244.908 s，输出 256 token 为 35.7 tok/s；
约 20%、50%、85% 位置的三个校验串都正确取回。续聊输入 204,297 token，复用 204,273，
只新读入 24，prefill 0.366 s，末段校验串再次正确。长输入运行期间遥测最低空闲为
2080 的 1,172 MiB、4080 的 1,580 MiB，未见显存持续增长或请求失败。
原始 204K 对照使用自动流送比例、K8V4、缓存关闭和 384 输出，本次是 0.5、K8V8、缓存开启、
256 输出，并经过 HTTP 模板，不能单独将两次差距归因于专家缓存扩容。

后续容量分析中 2,401 个未驻留专家、4.54 GiB RAM 等数字保留原始 profile 和预算口径，
当前启动配置以 [按需启动文档](IQ_KT_MODEL_SWITCH.zh-CN.md) 为准。

## 200K 调优：21＋27 层，4080 专家全部驻留

用户提出让 4080 再承担一层后，实际测试了 `--layer-split 21`，即 2080 跑 0–20 层，
4080 跑 21–47 层。它可以运行，无需新增跨卡专家调度功能。
移动一层给 4080 增加约 1.015 GiB 权重载荷，另有该层的状态和运行时分配。

对照均为 v4、200K 容量、K8V8、2048 prefill、MTP 关闭、`--pcie-frac 0.5`、
2080 预留 1,024 MiB、前缀缓存开启、同一 GPU 唤醒方式。相同 3,305-token 合成输入运行两次，
每次生成 256 token；第二次命中前缀。表中 decode 是总生成 token 除以总 decode 时间，不含 prefill。

| 方案：2080＋4080 | 4080 预留 | 总常驻专家 | 4080 未驻留专家 | 平均 decode | 4080 最低遥测空闲 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **22＋26，原配置** | 768 MiB | 22,426 | **0 / 13,312** | **40.96 tok/s** | 1,580 MiB |
| 21＋27 | 768 MiB | 22,698 | 268 / 13,824 | 39.70 tok/s | 1,054 MiB |
| 21＋27 | 512 MiB | 22,827 | 139 / 13,824 | 40.36 tok/s | 800 MiB |
| **22＋26，回切复测** | 768 MiB | 22,426 | **0 / 13,312** | **41.55 tok/s** | 1,580 MiB |
| **21＋27，200K 阶段采用** | **128 MiB** | **22,966** | **0 / 13,824** | **42.55 tok/s** | **532 MiB** |

21＋27 在 768 / 512 MiB 预留下让 2080 只处理 21 层，GPU 专家缓存也确实增加；RAM 专家从
4.07 GiB 降到 3.56 / 3.31 GiB。但 4080 不再满足整阶段全驻留条件，启动日志不再出现该阶段的
`100% VRAM resident: zero-doorbell graph`，未命中时也需要 CPU 或 USB4 流送。
这组结果未显示整体提速。较小预留的一次重复请求达到 41.3 tok/s，但其首轮为 39.5，
两次平均没有超过原配置，不能只挑最快一次。

这两种部分驻留方案图捕获时，4080 报告的 CUDA 可用显存为 599 / 345 MiB，低于遥测的 1,054 / 800 MiB。
按 profile 和实际 KT blob 大小计算，补齐剩余专家还需 530.48 / 275.35 MiB，
只算权重便会把相应 CUDA 余量压到约 69 / 70 MiB。最初据此恢复 22＋26，尚未尝试实际装齐。

这里“无法驻留”指在所选预留预算内装不全，并非已经尝试全部分配并遇到 OOM。
预留是配置选择；约 70 MiB 当时只是差值估算，不能作为全驻留会失败的证据。
NVML 遥测与引擎直接调用 `cudaMemGetInfo` 的读数确实不同，差额尚未逐项归因，
345 MiB 也不是从 800 MiB 再减一次 512 MiB 预留得到的。

随后按用户要求将 4080 预留进一步降至 **128 MiB**，实际装齐了全部专家：

| 阶段 | 层范围 | 常驻专家 | 专家显存 | RAM 专家 |
| --- | --- | ---: | ---: | ---: |
| 2080 Ti | 0–20 | 9,142 / 10,752 | 17,829 MiB | 1,610 个，约 3.04 GiB |
| 4080 SUPER | 21–47 | **13,824 / 13,824** | **26.69 GiB** | **0** |

合计 22,966 个专家、45,161 MiB，比原 K8V8 / 22＋26 多 540 个、1,044 MiB。
4080 的 `100% VRAM resident: zero-doorbell graph` 恢复启用。
捕获过程的 CUDA 可用显存依次约为 89、81、75 MiB；短、长及持续输出测试的 NVML 最低空闲
约为 532 MiB，没有观察到请求失败、显存持续增长或严重吞吐下降。结果证明这个配置在本轮负载下可用，
不应再把最初的预留预算当作无法装齐的硬件限制。

短输入两次分别为 **42.4 / 42.7 tok/s**，合计平均 **42.55**，比两组 22＋26 对照高约 2.4–3.9%。
回切对照的两次分别为 41.0 / 42.1 tok/s，说明这组小幅差距中也有测量波动。
同一配置的两次输出一致，改变分层或缓存后输出有差异；这是端到端生成对照，
不是固定输出 token 的算子消融，也没有用这几次输出判定质量升降。

另做两次各 **1,024-token** 持续输出，同为 3,305-token 输入：decode 为 **40.1 / 40.8 tok/s**，
第二次复用 3,298 token、新读入 7，prefill 0.107 s。最低遥测空闲约为 2080 的 1,164 MiB、
4080 的 532 MiB，测试通过。不同输出长度的速度不直接合并求平均。

完整长上下文也已验证：**204,018-token 输入、256-token 输出**，prefill **226.903 s**
（899.1 tok/s），decode **36.5 tok/s**，约 20%、50%、85% 位置的三个校验串均正确。
原 22＋26 同条件长输入为 244.908 s、35.7 tok/s；本次 prefill 耗时减少约 7.4%，
decode 小幅改善。每种长输入只有一次测量，不能当作多轮稳定增幅。

长输入第一次续聊的缓存断言未通过：两次请求之间另一客户端插入了 57,188-token 请求，
输出 2,048 token 后取消。当前多会话停放预算为 0，该请求替换了活动对话缓存，因此续聊重新读取
204,297 token。日志有 6 个检查点，没有检查点分配失败；这项受干扰的记录保留，不能写作命中成功。
重建该对话后立即追加的独立复核通过：**204,329 总输入，复用 204,306、新读入 23，prefill 0.484 s**，
正确返回 `amber-orchid-7391`。它验证了全驻留配置下的长前缀复用。

该阶段采用 **21＋27、预留 1,024 / 128 MiB、K8V8、prompt-cache 6**。
后续按用户要求恢复 256K，测试与当前选择如下。

## 当前方案：0.1.41、22＋26、256K、K8V8

上游升级的 A/B 先固定 21＋27 / 200K，结果见 [合并记录](IQ_KT_UPSTREAM_0.1.41_MERGE.zh-CN.md)。
随后保持 0.1.41，只把 `--layer-split 21` 改为 `22`、`--max-context 204800` 改为 `262144`；
prefill 2048、resident KV 20480、预留 1024 / 128、前缀缓存 6、pcie-frac 0.5、MTP 关闭和核显视觉均相同。

| 项目 | 21＋27 / 200K | 22＋26 / 256K |
| --- | ---: | ---: |
| 2080 / 4080 常驻专家 | 9,142 / 13,824 | 9,090 / 13,312 |
| 专家缓存总量 | 45,161 MiB | 44,070 MiB |
| 4080 常驻比例 | 13,824 / 13,824 | 13,312 / 13,312 |
| RAM 专家 | 1,610 个，3,117 MiB | 2,174 个，4,209 MiB |
| 4080 图捕获后 CUDA 可用 | 约 75 MiB | 约 1,059 MiB |
| 长测最低 4080 NVML 空闲 | 约 532 MiB | 约 1,518 MiB |
| 3,305-token 输入 decode | 42.84 tok/s | 41.43 tok/s |
| 9,769-token 输入 decode | 43.82 tok/s | 41.86 tok/s |
| 3,305-token 未缓存 prefill | 7.330 s | 7.272 s |
| 9,769-token 未缓存 prefill | 12.423 s | 13.045 s |

每种配置独立加载两次，每种长度共四个 256-token decode 样本；未缓存 prefill 各两次。
这是同日顺序对照，沿用相同唤醒方式，核心频率动态变化。平均 decode 慢 **3.3% / 4.5%**，
本组差值约 **1.4 / 2.0 tok/s**，不能固定理解为任何任务都只差 1 tok/s。
短输入输出文本一致，中输入同一配置内一致、跨分层有差异；CPU/GPU 放置改变可影响舍入和生成，
这些回答不用于判断模型质量升降。

更大的容量实际跑到了接近上限：

| 请求 | 输入 / 输出 token | Prefill | Decode | 检查 |
| --- | --- | ---: | ---: | --- |
| 首轮长输入 | 261,618 / 384 | 320.104 s（817.3 tok/s） | 36.6 tok/s | 20%、50%、85% 位置三个校验串正确 |
| 立即续聊 | 262,024 / 10 | 0.364 s | 39.7 tok/s | 复用 262,001，只读入 23，最后一个串正确 |
| 短输入持续输出 | 3,305 / 1,024 | 6.423 s | 39.7 tok/s | 正常完成 |

续聊总输入输出达到 **262,034 / 262,144**；容量由输入和输出共享，并非输入占满后还有额外输出空间。
长测最低 NVML 空闲为 2080 约 **1,157 MiB**、4080 约 **1,518 MiB**，未出现请求失败或显存持续增长。
21＋27 新版 204K 长测为 36.8 tok/s，但长度和输出数量不同，不把两者当作分层成本的独立消融。

这次将一层移回 2080，RAM 专家增加约 **1.07 GiB**，也让 4080 获得更多运行余量。
固定 resident KV 池不随最大容量线性增大；完整 KV 在 RAM，GPU 的 indexer 等状态仍会增加。
旧版 22＋26 / 200K 曾驻留 9,114 个主卡专家，新版 256K 为 9,090；版本也不同，
这 24 个槽的差不能全部归因于上下文一个因素。

按用户对完整上下文的偏好，已采用 **22＋26 / 256K / K8V8** 并恢复原 8080 服务。
**本轮没有测试 21＋27 / 256K**，200K 不是已证实的该分层硬上限；原配置仍保留本机备份。
完整脱敏记录见 [256K 基准](../bench/results/2026-10-08-v4-256k/README.md)。

## 优先尝试的优化

### 1. 用 v4 的实际路由更新专家缓存

当前仍用 `data/expert-profile.bin`，并设置 `--adapt-every 0`。这个选择便于做可重复的 A/B；
v2 全驻留时也无需换专家，但当前 22＋26 / 256K 的 v4 仍有 2,174 个专家在 RAM，静态通用排序未必适合当前任务。

已有功能可以在不重新量化权重的情况下改善它：

- 比较 `--adapt-every 4` / `8` 与每次 `--adapt-swaps 16` / `32`，记录换入开销和完整回答耗时。
  同层交换大小一致，适用于这个混合 KT 包；4080 已全驻留，没有需要换入的专家。
- 确认收益后再比较 `--adapt-async 1`，让 resident RAM 交换在后台推进。
- 用独立的 v4 `expert_profile_save` 文件保存学习结果，避免覆盖 v2 的 profile。
  保存功能要求 adaptation 已开启；只加保存路径而继续 `--adapt-every 0` 不会学习。
- 若要固定缓存做复现，用有代表性的路由 trace 生成独立 profile，并在未参与学习的任务上验证。
  `tools/make_profile.py` 必须用 `--reorder` 或 `--no-base`：默认只追加到已完整的 base，排序不会改变。

交换越频繁不一定越快。每个专家约 1.85 / 2.19 MiB，resident RAM 交换需要搬入和搬出；
应比较实际减少的 CPU/流送时间与交换成本。更好的缓存还不等于全驻留。
放置改变可能因 CPU/GPU 舍入差异改变生成文本，不能承诺逐 token 相同。

### 2. 为 12900HK 调整 CPU 线程和流送比例

启动日志是 14 个参与线程、每阶段 42 个 row tasks，即 6 个 P 核和 8 个 E 核都参与。
KT CPU 路径有查表、整数点积和阶段同步，小量未命中时，更多线程未必更快。

先保持缓存和 `pcie-frac=0.5` 不变，对照：

| 候选 | 用意 |
| --- | --- |
| `--pool-affinity p-cores --pool-workers 5` | host 加 5 个 worker，使用 6 个 P 核 |
| `--pool-affinity all --pool-workers 7` | 8 个参与线程，少量 E 核参与 |
| 当前默认 13 个 worker 加 host | 14 个参与线程的对照 |

再比较 `--pool-tasks 0` 和较细的任务划分，例如 96；任务数是整个 GU/Down 阶段的目标，
不是每专家线程数。选好 CPU 设置后，再细扫 `--pcie-frac 0.35/0.5/0.65/0.75`。
CPU 变快后最佳流送比例也可能变化，不应沿用一次启动的带宽探测当作最终最优值。

### 3. 检查部分命中时的 GPU 自主调度

源码已有 `STRATA_VERIFY_DEVICE_PLAN=1`：某次路由选出的专家都驻留时，在 GPU 上生成计划，
减少该组对 host 计划的等待；有未命中时仍保留回退。它不要求整层的 512 个专家都在显存。
默认关闭，上游其他机器的收益曾接近零；本机 KT/异构双卡尚未测过。

当前 2080 阶段无法满足“整个阶段全驻留”的条件，因此这个开关比 v2 时更值得单独 A/B。
它不会把 RAM 专家变成显存专家，也不保证消除全部 host 工作。

### 4. 按工作负载尝试不加载 MTP 的 prompt lookup

当前为了对照关闭了 `--suffix-draft` 和 `--lookup-chain`。Strata 可以在没有 MTP 权重时，
从上下文中重复的片段提出候选，再由主模型验证。代码补全、模板或重复结构可能受益；
普通问答、低命中任务也可能被额外验证拖慢。

这条路径没有约 1.54 GiB 的 MTP 侧车开销，但更宽的验证窗口仍占显存和计算。
开启 suffix 时要检查启动参数的自动扩窗逻辑；先控制窗口大小，再统计每窗口接受量和总耗时。
它不是未经主模型确认就复制文本，也不能把其他任务的高接受率当作本机收益。

## 显存还能省多少

### KV 与上下文：可以省，但规模不匹配

12 个 QSA 层、每层 20,480 resident cells，仅 GPU K/V 数据池：

| KV | 两卡合计 |
| --- | ---: |
| K8V8 | 247.50 MiB |
| K8V4（初始对照） | 191.25 MiB |
| K4V4 | 135.00 MiB |

从 K8V4 再降到 K4V4，只再省 **56.25 MiB**，同时降低 K 的精度，无法填补 4.54 GiB。
20,480 已是当前实现的 resident 下限，更小的参数会按下限处理。

降低 `max-context` 会缩小 RAM KV、indexer、RoPE 和部分工作区，但固定的 resident K/V 池不会随之缩小。
仅按源码可直接计算的 12 个 indexer 池、每卡共享的 RoPE 表、cell scores 和页表：
256K→200K 约省 113 MiB GPU 内存，200K→128K 再省约 145 MiB；这里未包含其他 prefill/verify 分配。
因此继续大幅牺牲上下文，不是恢复数 GiB 专家驻留的首选办法。

### 预留与分层：已实际验证 4080 全驻留

按初始 split 22 的 profile，额外给 2080 专家缓存 256 / 512 / 1024 MiB，大约能增加 131 / 264 / 528 个专家。
这有潜在收益，但距当时缺少的 2,401 个仍远。Windows 还要给 CUDA graph、唤醒 probe 和后续请求留空间；
过量分配可能被 WDDM 放到系统内存，结果更慢。需看请求运行后的显存驻留和速度，不只看启动成功。

split 22→21 给 4080 增加约 **1.015 GiB 权重载荷**，另有状态。
随后已做上面的 21＋27 对照：768 / 512 MiB 预留下分别缺 268 / 139 个专家，decode 没有明确收益；
之后在 128 MiB 预留下装齐，短输入、204K、持续输出及长前缀复用均已验证；后续为 256K 改回 22＋26。
遥测空闲与 CUDA 可分配量仍需区分，但较低的 CUDA 读数本身也不等于运行失败。

只统计全驻留权重、尚未加运行时的分层账目也说明限制：

| Split | 2080 权重 | 4080 权重 |
| --- | ---: | ---: |
| 19 | 20.41 GiB | 31.78 GiB |
| 20 | 21.42 GiB | 30.77 GiB |
| 21 | 22.43 GiB | 29.75 GiB |
| 22 | 23.44 GiB | 28.74 GiB |

两卡的 54 GiB 不是统一显存池。把分层点改回 19/20，本身不提供状态、工作区和驱动需要的空间。

## 需要改代码的方向

1. **KT CPU 算子。** 当前 `kt_avx2.cpp` 已有 trellis 查表和 AVX2 点积，但尚未接入上游其他
   i-quant 使用的 AVX-VNNI 路径。可在硬件支持检测后尝试，要求保持整数点积和浮点归约契约，
   先跑真实行数值对照，再测端到端；其他量化格式的收益不能直接套到 KT。
2. **RAM 中缓存已解码的 KT。** 保留 INT8 整数码和原 FP32 scale，可省重复 trellis 重建，
   不需要再次量化。但按初始 split 22 的 2,401 个 RAM 专家计算，全部展开需要额外约 **12.36 GiB RAM**。
   GPU 流送仍应保留原来紧凑的 4.54 GiB KT，不能把更大的展开格式送上 PCIe。
   适合先做有限容量的 CPU 热专家缓存；额外内存带宽和提交额度也要计入。
3. **减少权重副本和分配碎片。** 专家槽已经按各层实际大小分配，本包两种 blob 都满足
   256 字节对齐，没有靠“取消最大专家统一 padding”再省几 GiB 的空间。
   Native dense 的 2 MiB 粒度估算差额合计约 126 MiB，合并分配值得考虑，但不是实测可回收值。
   HC 当前还保留约 1.2 GiB 的 BF16 矩阵；让 decode/prefill 共用原生 Q8、按需解码有机会节省
   约 0.55 GiB，需要同时修改两条路径并核对舍入。
4. **KT prefill MMQ / grouped experts。** 当前仍有完整解码到 FP16 后矩阵计算的成本。
   专用量化矩阵乘法或融合多专家调度是较大的实现方向。也可先比较 2048/4096 分块；
   v2 的 4096 收益不代表 v4 已验证，prefill 提速也不等于单 token decode 提速。

两个容易误用的开关：

- `STRATA_Q8_PACKED=1` 当前会保留原 Q8，再增加 decode 用副本。按本机 v4 和 eligibility 条件，
  两卡分别新增约 882 / 1031 MiB，仅载荷就共 1.87 GiB，可能挤出更多专家。
- `STRATA_HC_Q8=1` 当前也是另加 Q8 副本，原 BF16 仍供其他路径使用；它本身不是省显存开关。

## 如果允许改变权重表示

把那 16 层 IQ4_KT gate/up 重新量化为 IQ3_KT，按布局可减少约 2.73 GiB；
部分 Q8 稠密权重也可改为更小的格式。但这些是在改变 v4 的量化方案，应生成独立模型包，
优先从原始高精度权重和适当 imatrix 量化，并重新做任务质量与长上下文评测。
不要直接把 v2 张量拼进 v4，就宣称仍是原版 v4 或没有质量变化。

## 后续验证顺序与证据

当前采用经验证的 22＋26 / 256K；下一步保持原版 v4，测独立 profile/adaptation、CPU 线程和更细的流送比例；
再测 device plan 和算子开发。每次只改变一个因素，同时记录完整请求耗时、prefill、decode、
CPU 专家时间、GPU 等待、换入成本、频率和显存余量。动态缓存要分别测刚启动与学习后的任务，
并用独立任务检查泛化；不能只在生成 profile 的同一提示词上报告收益。
