# 本机 GPU 唤醒与空闲功耗

2026-10-09，Windows / 2080 Ti 22 GiB + USB4 4080 SUPER 32 GiB。

## 谁负责什么

| 组件 | 职责 |
| --- | --- |
| Strata 引擎与服务 | 模型计算、专家缓存、KV、前缀缓存和 Web/API。 |
| [`tools/serve_gpu_wake.py`](../tools/serve_gpu_wake.py) | 根据加载、请求和卸载事件，调用本机已有 `B:/llama.cpp/proxy/gpu_monitor.py`。 |
| `GpuPowerManager` | 经 NVML 设置、释放两张卡的时钟锁；请求到来时在 4080 上运行短 CUDA 唤醒脉冲。 |
| NVIDIA 驱动 | 根据时钟约束和实际负载选择 P-state；解除锁频后才可以正常降频。 |

本机仍使用唤醒包装器，未启动原来的代理服务。包装器没有启动原代理的全局 AutoGuard 循环，
也不会持续执行 CUDA 脉冲。它保留 Torch/CUDA context，在需要时运行微型矩阵乘法。

朋友使用的 Windows CUDA 13 预编译包直接启动 `serve.server`，没有携带这套本机专用锁频模块，
也不依赖 Torch。CUDA runtime 的打包方式与空闲锁频是两件事。

## 本次修复

旧包装器在启动时执行 BOOST，但只在一次生成结束后安排 120 秒空闲计时。
因此，服务启动完成后如果没有收到生成请求，时钟锁就会一直保留。

修复后的行为：

- 模型加载完成后开始 120 秒计时，无须先发送一次请求。
- 请求到来时取消旧计时并提频；最后一个生成请求结束或取消后重新计时。
- 连续空闲 120 秒后释放两张卡的核心时钟锁，以及 4080 的显存时钟锁。
- 模型卸载、正常退出时释放锁频。预设切换先调用 `/unload`，可在 Windows 终止包装器前完成释放。
- 已取消的旧回调不会在新请求期间降频，也不会提前结束新一轮空闲计时；退出后不会再安排计时器。

10 项唤醒生命周期测试与 6 项预设切换测试通过。修改仅涉及 Python 包装器，未重建推理内核。

## 初始现场

API `/status` 为 `busy=false, queued=0`，模型保持加载。

| 显卡 | 修复前 P-state | 核心 / 显存时钟 | 功耗 |
| --- | --- | --- | --- |
| 2080 Ti | P5 | 1500 / 810 MHz | 27.66 W |
| 4080 SUPER | P2 | 2100 / 11251 MHz | 45.16 W |

在服务空闲时手动释放相同的 NVML 时钟锁，两卡均观察到 P8。4080 为 210 / 405 MHz、约 4.2 W；
2080 的核心仍会随桌面活动变化，显存降至 405 MHz，功耗约 26 W。Windows GPU 计数器同时报告
桌面合成器等图形负载，所以 P8 不代表整卡功耗必须低至几瓦。

释放锁频前后，模型的显存占用仍为 2080 20999 MiB、4080 30787 MiB。
模型常驻显存与进入 P8 可以同时成立；空闲降频不需要卸载模型。

## 部署后的验证

已在原 8080 端口部署，保持 v4、22＋26 分层、262144 上下文、K8V8 和核显视觉。
完整采样见 [`validation.json`](../bench/results/2026-10-09-gpu-idle/validation.json)。

1. 重启后没有生成请求：READY 后约 131 秒的采样中，两卡均为 P8，4080 为 4.27 W。
2. 发送 32-token 输入、生成 128 token：两卡恢复 P2，显存频率分别为 6800 / 11251 MHz。
3. 观察请求后的空闲时，中途又收到一条实际请求，计时被重新开始。该请求结束后，两卡再次自动
   进入 P8；最后一次采样为 2080 23.33 W、4080 4.03 W。API 仍报告模型加载和 262144 上下文。

120 秒计时只释放时钟锁，不清理 KV 或前缀检查点。部署时的进程重启会清掉 RAM 中的会话状态，
之后若短请求打断另一条长对话，还需要单独的多会话缓存；见[前缀缓存说明](IQ_KT_MODEL_SWITCH.zh-CN.md#前缀缓存)。
