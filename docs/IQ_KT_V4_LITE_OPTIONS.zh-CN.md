# v4 IQ3_KT 的低开销缩减方案

2026-10-09。目标是保留比 v2 更好的质量，同时降低 v4 的显存负担。初始分析读取本地 GGUF
头部、pack 索引和加载器源码，核算候选方案；随后补充专家和路由张量的完整字节比较。
后续按用户选择，将“v4 稠密权重＋v2 专家＋v2 PLE 表”制作为独立的 v4-lite，来源与运行记录见
[v4-lite 实测](IQ_KT_V4_LITE_2026-10-09.zh-CN.md)。本页的候选比较仍以静态核算为主；
**其他未制作方案的质量、速度和全驻留可行性尚未实测。**

最值得先比较两个候选：**v2 的专家和大矩阵＋v4 的 387 个高精度投影**，以及
**v4 的稠密权重＋全 IQ3_KT 专家**。前者最贴近“基本不增加 v2 的运行开销”，后者保留更多 v4 设置。

## 预算与瓶颈

本机为 RTX 2080 Ti 22 GiB＋RTX 4080 SUPER 32 GiB。最近的
[同机性能测试](IQ3_XXS_VS_V4_2026-10-09.zh-CN.md)中，v4 仍有 4,250 MiB 专家在 RAM，
IQ3_XXS 则全部驻留双卡。优化时要分别满足每张卡的预算，不能只减小 GGUF 的磁盘大小。

下表统一按 **19＋29 分层**统计 GPU **权重载荷**，包括专家、加载后的稠密权重和输出头；
不含 KV、其他状态、工作区、CUDA graph、驱动、分配粒度和显存预留。

| 方案 | GPU 权重载荷 | 比原 v4 少 | 主要取舍 |
| --- | ---: | ---: | --- |
| 原 v2 | 47.84 GiB | 4.34 GiB | 已有速度基线 |
| 原 v4 | 52.19 GiB | — | 精度基线 |
| v2＋v4 的 387 个投影 | 47.84 GiB | 4.34 GiB | 与 v2 相同的运行存储格式、尺寸和运算规模，质量收益待测 |
| v4 稠密权重＋全 IQ3_KT 专家 | 49.45 GiB | 2.73 GiB | 保留 v4 稠密精度，取消 16 层专家 gate/up 的 IQ4_KT 升级 |
| 上项＋三类 GDN 大矩阵 Q6_K | 48.99 GiB | 3.20 GiB | 额外节省 479.53 MiB，需要重新量化并测损失 |

矩阵尺寸、48 层、每层 512 个专家、每 token 选 10 个专家均保持原样。
因此没有增加矩阵乘法规模；不同量化的反量化指令、内存带宽与内核效率仍可能改变实际耗时。

## 方案一：v2 加入 v4 的 387 个高精度投影

逐张量核对发现，下列张量的 v2/v4 源格式不同，但两个 pack 中的目标字节数、目标类型和
量化标记完全相同。它们在当前路径中均作为 BF16 运算，合计约 1.257 GiB：

| 部分 | 张量数 | 精度变化的来源 |
| --- | ---: | --- |
| 每层 HC 投影及最终输出 HC | 290 | 源权重 IQ4_KT → Q8_0，运行时均为 BF16 |
| SSM alpha / beta 小投影 | 72 | 源权重 IQ4_KT → Q8_0，运行时均为 BF16 |
| QSA indexer 的 Q/K 投影 | 24 | 源权重 IQ4_KT → BF16，运行时均为 BF16 |
| PLE value 投影 | 1 | 源权重 IQ4_KT → Q8_0，运行时均为 BF16 |

v2 从低位权重展开到 BF16，不会恢复量化时丢失的信息；换成 v4 的值，有机会减少这部分误差，
同时维持 v2 的 GPU 权重载荷与计算形状。核算覆盖 18–22 各分层点，载荷均与对应 v2 相同。

这个方案保留 v2 的大块原生稠密矩阵、输出头、专家和 PLE 表，未保留 v4 所有升级。
**不能从 387 个张量的数量推算能保留多少 v4 质量收益，也不能保证所有任务都强于 v2。**
但它很适合先做一次独立候选，测是否能以接近 v2 的开销得到实际提升。

磁盘方面，保留 v2 PLE 时，张量载荷增加约 375.55 MiB；这是显存与运行成本优化，
不是该分支的磁盘压缩。可另外比较换成 v4 PLE 的版本：张量载荷约 68.10 GiB，
但 PLE 从 IQ4_KT 变成 IQ3_KT 是另一项精度变化，应分开验证。

## 方案二：保留 v4 稠密精度，取消专家的 IQ4_KT 升级

v4 只有第 **0–5、38–47 层**的专家 gate/up 从 v2 的 IQ3_KT 提高到 IQ4_KT；
专家 down 仍为 IQ3_KT。每层把 gate/up 一起恢复为 IQ3_KT，精确节省 **175 MiB**，
16 层合计 **2,800 MiB / 2.734375 GiB**。

这样保留 v4 的 HC、SSM、indexer、QSA、共享专家、输出头及 PLE 设置，专家总量从
47.15 GiB 降至 44.41 GiB。它比方案一保留更多 v4 的高精度稠密表示，是偏向质量的候选。

已有[发布说明的本地记录](IQ_KT_V4_ANALYSIS.zh-CN.md#kld-下降主要来自什么)报告：
v4 IQ3_KT 相比 v2 的英文/代码平均 KLD 约下降 42%；同一作者的 IQ4_KT 对照中，
专家和 PLE 不变，其他权重升级也带来明显 KLD 改善。这支持优先保留稠密精度，
但不是对这个混合候选的实测，也不能把改善比例直接套过来。本次未重新取得该固定版本的远端 README。

现成 v2 文件已经含有这 32 个 IQ3_KT gate/up 张量，可作为独立候选的来源，避免先把
v4 IQ4_KT 反量化再量化成 IQ3_KT。制作时仍需确认源模型对应关系，并校验类型、形状和偏移。
当前 `native_experts.txt` 支持每角色指定源分片，源码会校验每个张量的实际范围；
具备复用既有 GGUF 字节的基础，不必先重新量化整个模型。这样的候选需要独立命名和配置。

## 专家校准与复用风险：完整字节核验

为核对 v2 专家能否作为方案二的来源，补充读取了两版全部同格式 routed-expert 张量和
`ffn_gate_inp.weight` 路由矩阵。逐块直接比较每个字节，同时记录逐张量 SHA-256，结果如下。
层号从 0 开始，每个专家张量包含该层全部 512 个专家。

| 部分 | 张量数 | v2 → v4 | 完整比较结果 |
| --- | ---: | --- | --- |
| 全部 48 层的 expert down | 48 | IQ3_KT → IQ3_KT | 全部逐字节相同 |
| 第 6–37 层的 expert gate/up | 64 | IQ3_KT → IQ3_KT | 全部逐字节相同 |
| 第 0–5、38–47 层的 expert gate/up | 32 | IQ3_KT → IQ4_KT | 格式改变，未作同格式字节比较 |
| 全部 48 层的 router | 48 | F32 → F32 | 全部逐字节相同 |

因此，**v4 中保留 IQ3_KT 的 112 个专家张量，与本地 v2 完全一致**，每版共 34.609375 GiB。
两版合计读取 69.6875 GiB（含 router），耗时 76.079 秒；文件大小和修改时间在检查前后不变。
比较范围不含不同格式的 32 个专家张量的内容校验，也没有计算整个 GGUF 的哈希。

两版 GGUF 都记录 `qwen4exp-agentic-v3.imatrix`、`calibration-qwen4exp-v3.txt`、818 个条目、
2800 个 chunks；imatrix 路径写法不同，但文件名相同。发布说明的本地副本把这些版本列为同一
Uncensored 源模型的量化，并说明 imatrix 在原始 base 模型上生成。这里没有原始 imatrix 或
高精度源文件的哈希，不能仅凭同名元数据证明它们的文件身份。完整字节比较直接验证了上述
112 个专家张量的量化结果相同。

对于改变格式的 **32 个 gate/up 张量**，量化前的 BF16 权重按发布说明来自同一源模型；
本地没有逐项核验这些高精度原值。量化后的实际数值不能套用上述 112 个张量的相同结论。
补充使用 `tools/kt_quants.py`，逐张量解码展平后的首行、中间行和末行，共比较每版
245,760 个对应位置：32 个张量都出现数值差异。例如 `blk.0.ffn_gate_exps.weight` 第 0 行
第 0 列，v2 为约 −0.04095182，v4 为约 −0.04104143。这是抽样解码比较，不是完整数值扫描；
没有对应 BF16 原值，不能据两种近似值之间的差计算哪版的量化损失。
详见 [promoted-value-samples.json](../bench/results/2026-10-09-iqkt-lite-analysis/promoted-value-samples.json)。

“本机无需重新校准”指复用现有张量，不表示发布时没有使用校准。发布者所列的
`d9e2868` 量化器按张量查找 imatrix，并将其与浮点源权重一起传给 CUDA 量化接口；
校准统计指导量化值和缩放的选择。这个步骤不等于重新训练 BF16 权重。
本地没有发布者逐张量量化日志或原始 imatrix，不能由文件级元数据单独确认每项校准覆盖。

**直接复用 v2 已量化的 32 个 gate/up 张量，会保留其量化值和缩放等编码信息，不需要本机
重新计算 imatrix。** 方案二实施正确时，全部 routed-expert 权重将逐字节等于 v2；不存在先把
v4 IQ4_KT 展开、再无校准压回 IQ3_KT 的额外量化步骤。路由矩阵相同也不保证每个 token 选择
相同专家，因为稠密权重改变后，输入路由器的激活可能改变。

这仍不能保证方案二在整体质量上不低于 v2。除了各部分误差的相互作用，原方案二保留的
**v4 PLE 表是 IQ3_KT，而 v2 PLE 表是 IQ4_KT**；取消专家的高位升级后，这项降位仍然存在。
更保守的独立对照可采用 **v2 专家＋v4 稠密权重＋v2 PLE 表**，先减少 PLE 降位这一变量。
相对原方案二，PLE 张量载荷增加约 **4.7684 GiB**；按当前 SSD direct 的放置方式，前述 GPU
权重载荷仍约 49.45 GiB。矩阵尺寸和乘加规模不变，但 PLE 读取字节量、解码耗时及缓存占用
仍可能改变，应实测。该组合已按用户选择制作，具体来源检查和性能、基本能力验证见
[v4-lite 记录](IQ_KT_V4_LITE_2026-10-09.zh-CN.md)；不能仅凭 PLE 位宽推断质量。

方案一、二可以复用发布者已量化的张量；方案三的 Q8_0 → Q6_K 则会产生新的量化误差，
需要另外验证。此前对性价比的排序是候选优先级，不能当作混合版本已优于 v2 的结论。
完整清单与哈希见 [expert-identity.json](../bench/results/2026-10-09-iqkt-lite-analysis/expert-identity.json)，
方法见 [compare_experts.py](../bench/results/2026-10-09-iqkt-lite-analysis/compare_experts.py)。

## 能否只校准并重做这 32 个张量

可以把最终重新量化的范围限定为第 0–5、38–47 层的 gate/up。应分别处理两个阶段：

1. **采集 imatrix**：用有代表性的中文、代码、工具调用等样本跑前向，记录目标张量输入的
   重要性统计。目标包含最后一层，因此仍需执行前面的网络计算；只采集这些层不能省去这些
   前向依赖。可先用现有 v4 采集，但这是基于量化模型的近似统计，不等同于 BF16 参考校准。
2. **生成新 IQ3_KT 权重**：用同一来源的 BF16 原权重和新统计，重新量化目标张量，然后在独立
   pack 中引用结果。其余权重保持原字节。只重收 imatrix 不会改变现有 GGUF，必须重新生成
   量化权重；从 v4 IQ4_KT 解码后再做 IQ3_KT 仍属于二次量化，不能恢复已丢失的 BF16 信息。

本地 `ik_llama.cpp` 检出为 `c68d4e3c85ba45f713187f0932b42bf6b34e79b8`。源码有
`llama-imatrix` 采集器、IQ3_KT/IQ4_KT 的 CUDA 量化接口、`--custom-q` 张量精度规则和
`--slab-size` 分批量化。采集器当前会收集所有符合条件的 MoE 运算；若只想采集目标层，需加
名称过滤，或先采集再筛选。量化器的 `--include-weights`/`--exclude-weights` 只筛选使用哪些
imatrix 条目；`--partial-requant` 只跳过已有输出分片，都不能当作“只量化这些层”的开关。
独立目标张量工件的生成与加载还没有做端到端验证。

在 `B:/models/llm/Qwen/Qwen3.8-Flash-Next` 未找到主模型 BF16/F16 GGUF 或 safetensors；
其中的 F16 文件是视觉投影，不能提供这些专家权重。该目录及工作区未找到 `.imatrix` 或
`imatrix*.dat` 文件。工作区存在其他版本的 `llama-imatrix.exe`/`llama-quantize.exe`，但
`ik_llama.cpp` 检出中未找到这两个可执行文件，不能把其他构建当作已验证的 KT 工具。

每个目标张量形状为 `[2560, 640, 512]`，BF16 载荷 **1.5625 GiB**；32 个共 **50 GiB**。
这是目标原权重的净数据量，实际下载量取决于源分片和是否能按范围提取。可逐张量或按专家
分批量化，不要求把全部 50 GiB 同时放入显存。输出 IQ3_KT 载荷为 **9.8046875 GiB**，相对
v4 的这部分节省 **2.734375 GiB**；更换 imatrix 不会改变固定形状、固定格式的容量。

本机具备进行此类分批量化和前向采集实验的硬件条件，但尚未验证该校准程序在本机的加载、
峰值资源和速度。重算统计、量化和验证增加的是制作阶段开销，部署后不需要运行 imatrix
采集器，推理矩阵规模不增加。已有在线模型占用双卡显存，实际采集须另行安排运行资源。

先用少量层做可行性试验，再扩展到 16 层；校准集与验证集应独立，并检查每层 512 个专家的
采样覆盖。当前采集器对缺少数据的专家可能跳过条目或填充值，因此输出了 imatrix 文件
不代表覆盖充分。新的局部校准是否比原作者 imatrix 或直接复用 v2 更好，仍需比较质量；
不能预先保证 IQ3_KT 能保留原 IQ4_KT 的质量。这一节是可行性核对，未下载原权重、采集
imatrix、编译或运行新量化工具，也未改动在线模型。

## 为什么还要改分层

当前 22＋26 分层中，以上 2.73 GiB 节省只有 **1.03 GiB** 在 2080，另 **1.71 GiB** 在 4080。
缩减后的 2080 仅权重仍需 **22.42 GiB**，已超过这张卡的容量。

| 候选 | 分层 | 2080 权重载荷 | 4080 权重载荷 |
| --- | --- | ---: | ---: |
| v4 稠密＋IQ3_KT 专家 | 22＋26 | 22.42 GiB | 27.03 GiB |
| v4 稠密＋IQ3_KT 专家 | 19＋29 | 19.38 GiB | 30.07 GiB |
| 再将三类 GDN 矩阵改为 Q6_K | 19＋29 | 19.19 GiB | 29.80 GiB |
| v2＋387 个投影 | 19＋29 | 18.80 GiB | 29.04 GiB |

19＋29 更值得先试，但 4080 的余量仍要供 KV 和工作区使用。表中载荷小于显存容量，
并不证明全驻留成功；应保留当前上下文和 KV 条件，实际加载后检查专家数量并跑长输入。

## 需要再省一点时

在方案二上，将 `attn_qkv.weight`、`attn_gate.weight`、`ssm_out.weight` 从 Q8_0 改为 Q6_K，
共 108 个矩阵，可再省 **479.53 MiB**；按 19＋29 分层分别是 **199.80 / 279.73 MiB**。
这三个角色的输入维度均符合 Q6_K 的 256 元素块要求，现有 CUDA 原生矩阵路径支持该格式。

先保留 HC、SSM 小投影、indexer、共享专家、QSA 和输出头的 v4 设置，便于判断这一项的损失。
Q6_K 只是比直接退回 v2 低位稠密表示更温和的候选选择，不能预先保证损失很小。
如果扩大到 QSA 的 `attn_q` / `attn_output`，合计节省 610.31 MiB，但应作为另一次对照。

优先用同一高精度源权重和合适的 imatrix 重新量化这些矩阵；Q8_0 → Q6_K 也属于二次量化。
现有 `tools/kt_quants.py` 是解码工具，不是 KT 量化器。无需重新量化未改变的张量。

## 不优先采用的办法

- **按专家使用频率逐个降位数**：当前格式按层记录 gate/up、down 类型，并要求同层 gate/up 类型相同。
  一个张量内 512 个专家不能直接各用一种位数；还需要改布局和调度。低频也不等于不影响罕见任务。
- **裁层、删专家、减少每 token 专家数**：会改变网络行为，通常比重新分配量化精度更需要校准或训练。
- **只压缩 PLE 大表**：当前 PLE 在 SSD，减少文件大小不会等量释放专家显存。
- **把小投影重新压低**：上述 387 个张量仍会展开为相同 BF16 大小，损失精度却不节省当前运行载荷。
- **直接打开 HC_Q8 / Q8_PACKED**：当前实现增加副本，不是现成的显存压缩开关。

## 建议的验证顺序

已先制作“v4 稠密＋全 IQ3_KT 专家＋v2 PLE 表”，以相同设置的 v2 和当前 v4 为对照。
“v2＋387 个投影”仍是尚未实测的另一候选。
先核对实际驻留与显存余量，再使用相同中文、代码、工具调用样本比较 NLL/KLD 和任务成功率，
并补测长上下文。候选二若接近显存边界，再试 GDN Q6_K；不要把几项改动一次混在一起归因。

这种比较才可以确认哪个候选同时满足质量和速度目标。此前的合成检索通过不能替代这项质量评测。
性能测量仍应保持相同提示词、输出长度、采样、缓存状态和 GPU 唤醒策略。
