# 本机 v2 / v4 按需启动

2026-10-08：两个模型及模型包都保留在本机。每次运行一个预设，共用 `0.0.0.0:8080`、
原来的 API key、Web 控制台和 Intel 核显视觉编码器。

## 启动入口

在 `B:/llama.cpp/Strata` 中双击对应文件：

| 入口 | 作用 |
| --- | --- |
| `run-strata-v2.bat` | 启动或切回 v2 |
| `run-strata-v4.bat` | 启动或切到 v4 |
| `run-strata-stop.bat` | 等待当前请求结束，关闭服务并释放模型资源 |

同名 `.ps1` 也可直接运行。原来的 `run-strata-vision-igpu.ps1` 现在通过同一套切换逻辑选择 v2。

入口会等待正在进行的请求结束，卸载旧模型后启动所选模型；加载期间 API 暂时不可用。
看到 `READY` 即可使用。服务在后台运行，启动窗口关闭后仍会继续运行。
重复选择已经加载的模型会直接返回，不重新分配显存。

Web 地址是 `http://10.0.0.3:8080`，API 地址是 `http://10.0.0.3:8080/v1`。
本机也可访问 `http://127.0.0.1:8080`。

查看当前选择：

```powershell
.\run-strata.ps1 -Model status
```

也可以使用 `-Model v2`、`-Model v4` 或 `-Model stop`。入口默认使用 8080。

## 两套配置

| 参数 | v2 | v4 |
| --- | --- | --- |
| 上下文容量 | 262,144 | 204,800 |
| KV | K8V8 / `int8` | K8V8 / `int8` |
| GPU 层分配：2080 / 4080 | 19 / 29 | 21 / 27 |
| GPU 常驻 KV cells | 20,480 | 20,480 |
| Prefill chunk | 2,048 | 2,048 |
| 前缀缓存 | `--prompt-cache 6`，RAM 检查点 | `--prompt-cache 6`，RAM 检查点 |
| 显存预留：2080 / 4080 | 1,536 / 768 MiB | 1,024 / 128 MiB |
| MTP | 关闭 | 关闭 |
| 未命中专家的 GPU 计算比例 | 按链路自动选择 | `--pcie-frac 0.5` |
| PLE 大表 | SSD direct | SSD direct |
| 视觉设备 | Intel Iris Xe | Intel Iris Xe |

v4 的 0.5 比例来自初始 K8V4 配置下 3,570 输入、每次生成 256 token 的两轮补测：38.09 tok/s；
自动比例为 34.12，1.0 为 31.89。它是本次三个比例中最快的一项。
同阶段的 200K 长输入基准使用自动比例，不能把 38.09 当成长上下文速度。

v2 更适合优先追求当前已测吞吐，v4 用于试用新的量化方案和能力；版本号本身不能替代任务质量评测。
相同 200K/K8V4 对照中，v2 在 3,570 输入后约 60.46 tok/s，v4 的自动比例约 34.27 tok/s。
权重变化、完整基准和仍可尝试的优化见 [v4 显存与优化分析](IQ_KT_V4_ANALYSIS.zh-CN.md)。

2026-10-08 晚间先将 v4 改回 K8V8、降低 2080 预留，再实际尝试让 4080 多承担一层并装齐专家。
**当前已采用 21＋27、预留 1,024 / 128 MiB。** 含视觉的服务实际缓存 **9,142 + 13,824** 个专家，
合计 **45,161 MiB**；4080 负责的 **13,824 / 13,824** 个专家全部驻留，进入全驻留 CUDA graph。
2080 仍有 1,610 个专家在 RAM，约 **3.04 GiB**。相比上一套 K8V8 / 22＋26，多驻留
**540 个专家、1,044 MiB**。其他程序占用显存时，自动缓存大小可以变化。

K8V4→K8V8 的 resident K/V 池合计只增加 56.25 MiB GPU 内存；完整 200K RAM KV 池增加
562.5 MiB。两张卡的空闲不能合并使用；本次通过移动分层点增加 4080 负责的专家。
启动入口不变，本机 v4 JSON 文件名保留历史 `dual22-k8v4` 字样，实际参数为
`--layer-split 21 --kv int8 --vram-reserve-later-mib 128`。

相同 3,305-token 输入、各两次 256-token 输出，21＋27 在 4080 预留 768 / 512 MiB 时
分别缺 268 / 139 个专家，平均 decode 为 39.70 / 40.36 tok/s；22＋26 对照为 40.96，回切复测 41.55。
随后预留降到 128 MiB、4080 专家全部驻留后为 **42.55 tok/s**（42.4 / 42.7）。
另做两次 1,024-token 持续输出，为 **40.1 / 40.8 tok/s**，没有观察到显存持续增长或请求失败。
图捕获时 4080 的 CUDA 可用显存最低约 75 MiB，测试遥测最低约 532 MiB；两者口径不同。
这次已验证较小预留下可以运行，之前“装不全”仅是 768 / 512 MiB 预算下的结果。
完整布局、显存口径与测试限制见 [v4 分层实测](IQ_KT_V4_ANALYSIS.zh-CN.md)。

`--spec 3` 保留验证窗口配置；两个预设都没有 `--mtp`，因此不会加载 MTP 草稿模型。

两套预设当前均使用静态专家 profile，动态交换关闭；v4 是否启用学习缓存、调整 CPU 线程或
GPU 调度还需独立对照。分析文档列出的候选开关没有自动加入这两个启动入口。

## 前缀缓存

2026-10-08 晚间恢复日常使用的 `--prompt-cache 6`，两个预设均已保存。此前为了基准关闭缓存的
设置没有及时恢复，导致续聊反复处理完整历史。现在最多保留 6 个检查点，位于 RAM；
上游给出的典型大小约 118 MB/个，具体取决于模型状态。新读入提示词每 16,384 token 建立一次
周期检查点，系统提示词的 root 检查点阈值为 2,048 token，均沿用引擎默认值。
单独的多会话停放预算 `--conversation-cache-mib` 仍关闭。

复用要求实际 token 前缀相同；续聊和从旧消息分支都可命中。重启、切换模型后第一次请求仍需
完整 prefill，这些检查点不跨进程持久保存。API 返回的
`usage.prompt_tokens_details.cached_tokens` 可以直接检查命中量。

首次重启后的 K8V4 验证使用约 5.7K token 的合成记录，续聊和分支均正确取回校验串：

| 请求 | 总输入 | 复用 | 新读入 | Prefill |
| --- | ---: | ---: | ---: | ---: |
| 第一次 | 5,739 | 0 | 5,739 | 9.866 s |
| 续聊 | 5,767 | 5,741 | 26 | 0.380 s |
| 从第一轮分支 | 5,767 | 5,732 | 35 | 0.484 s |

这是减少重复 prefill 的收益，不能当作 decode tok/s 的增幅，也不保证不同提示词同样命中。
这次只启用检查点时，专家槽仍为 8,863 + 13,312，没有减少。
本机证据：`build-kt/prefix-cache-validation.json` 和 `strata-v4-vision-igpu.log`。

随后切换 K8V8、扩大专家缓存的 22＋26 配置中，3,305-token 合成输入生成 256 token 为 39.5 tok/s；
重复请求复用 3,298 token，只读 7 个，prefill 0.106 s、decode 40.6 tok/s。
这是当时设置的运行验证，没有取得本轮同条件旧设置基线，不能作为新增专家的净加速比例。
证据：`build-kt/v4-kv-cache-after.json`。

同一 22＋26 配置还通过 204,018-token 长输入测试：prefill 244.908 s，生成 256 token 为 35.7 tok/s，
正确取回约 20%、50%、85% 位置的三个校验串。续聊总输入 204,297 token，复用 204,273，
只新读入 24，prefill 0.366 s，再次正确取回最后一个串。整个测试中遥测最低空闲约为
2080 的 1,172 MiB、4080 的 1,580 MiB，未见显存占用持续增长。
这是当前机器下的容量、检索和前缀复用验证，不代表其他程序占用显存后仍有相同余量。
证据：`build-kt/v4-kv-cache-long.json`。

当前 **21＋27 / 4080 全驻留**也完成相同 204,018-token 输入和 256-token 输出：prefill
**226.903 s**、decode **36.5 tok/s**，三个检索串均正确。随后一次续聊检查被另一客户端的
57,188-token 请求插入打断；该请求输出 2,048 token 后取消，而多会话停放关闭，导致续聊重读历史。
那次缓存断言未通过的原始记录保留，不能算作前缀命中成功，也没有发现检查点分配失败。

重建该对话后立即续聊的独立复核通过：总输入 **204,329**，复用 **204,306**，新读入 **23**，
prefill **0.484 s**，正确取回首个校验串。测试期间最低遥测空闲约为 2080 的 1,164 MiB、
4080 的 532 MiB。当前保持这套 v4 在线。
证据：`build-kt/v4-kv-cache-split21-full-long.json`、`v4-full-prefix-followup.json`、
`v4-kv-cache-split21-full-stress.json`；比较口径见 [v4 分析](IQ_KT_V4_ANALYSIS.zh-CN.md)。

## API 模型名称

v4 的主名称为 `qwen3.8-flash-next-v4-iq3kt`；原来的
`qwen3.8-flash-next-iq3kt` 保留为别名，已有 harness 可以继续使用原地址、凭据和模型名称。
v2 的主名称仍是 `qwen3.8-flash-next-iq3kt`，另有明确的 v2 别名。

启动入口决定当前服务加载哪套权重。API 请求中的 `model` 字段和 Web 的加载/卸载按钮
不会把当前预设切换成另一套权重。可在 Monitor 或 `/v1/models` 中查看当前主名称。

## 实现与验证

通用工具为 `tools/switch_preset.py`，读取本机的 `strata-models.json`。
目录只列出允许管理的配置；工具仅管理同一工作区的 `serve_gpu_wake.py` 及其子进程。
端口被无关程序占用、目标文件缺失或当前请求未结束时，不启动另一个模型。
进程间锁串行化切换；新模型启动失败时会尝试恢复旧模型。

本地配置、启动器、模型包、日志和 API key 不提交到 Git。两个配置中的 key 必须一致；
工具不会输出 key。切换状态保存在 `strata-active.json`，启动日志位于 `logs/presets/`。

验证记录：

- `python -B tools/test_switch_preset.py`：6 项行为测试通过，覆盖进程归属、无关端口、
  缺少模型包、忙碌状态、失败恢复和重复启动。
- 实际 v2 → v4 切换成功；重复执行 v4 入口保持同一个服务 PID。
- `10.0.0.3:8080` 的 Web 返回 HTML，LAN API 正确列出 v4 及原模型名别名。
- 无凭据 API 请求返回 401；使用原模型名和原 key 的文本请求返回 `V4_READY`。
- 512 像素测试图通过 HTTP 正确识别 `TEST 421` 及从左到右的红、绿、蓝。
  编码器使用 `Intel(R) Iris(R) Xe Graphics`，`CUDA_VISIBLE_DEVICES=-1`，没有 Vulkan 数字过滤。

本机证据：`build-kt/v4-switch-validation.json`、`build-kt/v4-switch-start.log`、
`build-kt/v4-review-results.json`。最后保持 v4 在线供能力测试。
