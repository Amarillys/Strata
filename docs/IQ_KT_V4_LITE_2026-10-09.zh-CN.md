# v4-lite：v4 稠密权重＋v2 专家和 PLE 表

搬到另一台电脑运行时，现已另行导出完整的
[v4-lite 主模型＋独立 IQ4_KT PLE GGUF](V4_LITE_STANDALONE_GGUF.zh-CN.md)：
49.52＋25.03＝74.55 GiB，两份文件即可携带全部权重。该导出与本文权重组合一致；
本文原有本机预设仍引用原 v2/v4 分片，尚未切换到新文件。

给只有同款 v4 的接收者，另提供了约 9.80 GiB 的
[专家增量补丁](V4_LITE_PATCH.zh-CN.md)，附原始 v2 替换权重、应用脚本与 AI 提示词。
分享包默认保留原 v4 IQ3_KT PLE；本记录的本机部署使用 v2 IQ4_KT PLE。
打包验证见 [补丁结果](../bench/results/2026-10-09-v4-lite-patch/README.md)。

2026-10-09，按用户选择制作的独立组合。它直接复用已有量化字节，没有把 v4 解码后再次量化，
也没有在本机重新采集 imatrix。原 v2/v4 文件和预设保留。

采用 19＋29 分层、960/512 MiB 显存预留后，本轮生成速度比原 v4 高约 **26%–30%**，
仍比相同运行参数的 v2 低约 **14%–18%**。基本能力小样本未测出质量差距，不能据此承诺强于 v2。

## 权重来源

| 部分 | 实际来源 | 说明 |
| --- | --- | --- |
| 稠密权重、共享专家、输出头、token embedding | v4 | 保留 v4 的表示 |
| HC、SSM alpha/beta、indexer Q/K、PLE value 等 387 个投影 | v4 | 已包含在稠密部分，不是再添加一份 |
| 48 层 gate/up/down，共 144 个 routed-expert 张量 | v2 | 全部 IQ3_KT，包含每层 512 个专家 |
| `per_layer_token_embd.weight` 大表 | v2 | IQ4_KT；v4 的这张表是 IQ3_KT |
| PLE key/value 投影 | v4 | 与 PLE 大表的来源分别指定 |
| tokenizer、chat template、视觉配置 | v4 | Intel Iris Xe 视觉路径保留 |

387 个投影包括 290 个 HC 投影、72 个 SSM alpha/beta 投影、24 个 indexer Q/K 投影和
1 个 PLE value 投影。v2/v4 都将这些投影展开为 BF16 运算，但 v4 的源表示精度更高。

## 容量口径

专家张量从原 v4 的 **47.1484375 GiB** 降到 **44.4140625 GiB**，减少 **2.734375 GiB**。
在 19＋29 分层下，GPU 权重载荷约 **19.3836＋30.0697＝49.4533 GiB**，不含 KV、工作区、
图、分配粒度和驱动。矩阵尺寸、层数、每层专家数和每 token 选中的专家数保持原样。

v2 的 PLE 大表为 **25.0341 GiB**，比 v4 多 **4.7684 GiB**，沿用 SSD direct。
因此这是减少专家负担的组合；若把所选张量另行打成一个独立 GGUF，逻辑张量载荷相对 v4
反而净增约 **2.0340 GiB**。高位宽 PLE 不等于已经证明回答质量更好。

本文初次建立组合时没有生成独立合并 GGUF；后续完整导出见开头链接。原 pack 复制了约 1.4 GiB 的 v4
稠密文件和 tokenizer，专家和原生矩阵直接引用原 GGUF。使用此预设需要保留 v2/v4 的两个分片。

## 实测结果与预留选择

以下为每组固定生成 256 token 的 decode 中位数；采样和重复次数见后文。
v2 使用匹配当前引擎、上下文、缓存的临时配置，原 v4 使用已有的 22＋26 分层。

| 输入 token | 原 v4 | v4-lite（960/512 MiB） | 匹配配置的 v2 |
| ---: | ---: | ---: | ---: |
| 3,305 | 41.64 tok/s | **53.23 tok/s** | 63.78 tok/s |
| 9,769 | 40.63 tok/s | **52.70 tok/s** | 63.73 tok/s |
| 32,768 | 39.55 tok/s | **49.72 tok/s** | 60.80 tok/s |
| 128,000 | 37.85 tok/s | **47.56 tok/s** | 55.01 tok/s |

| 输入 token | 原 v4 TTFT | v4-lite TTFT | 匹配配置的 v2 TTFT |
| ---: | ---: | ---: | ---: |
| 3,305 | 6.784 s | 6.358 s | 5.906 s |
| 9,769 | 13.610 s | 12.544 s | 11.353 s |
| 32,768 | 37.336 s | 34.423 s | 29.888 s |
| 128,000 | 147.674 s | 134.871 s | 117.954 s |

TTFT 包含请求、会话处理、prefill 和首 token，不是纯 prefill 时间。速度收益同时包含权重
表示、分层和专家驻留的影响，不是某一个投影的单独收益。

| 引擎加载指标 | 原 v4 | v4-lite | 匹配配置的 v2 |
| --- | ---: | ---: | ---: |
| GPU 专家槽 | 22,381 / 24,576 | 24,156 / 24,576 | 24,576 / 24,576 |
| 2080 专家槽 | 9,069 / 11,264 | **9,728 / 9,728** | 9,728 / 9,728 |
| 4080 专家槽 | 13,312 / 13,312 | 14,428 / 14,848 | 14,848 / 14,848 |
| GPU 专家缓存 | 44,029 MiB | 44,702 MiB | 45,479 MiB |
| RAM 专家 | 4,250 MiB | **777 MiB（约 0.76 GiB）** | 0 MiB |

自动缓存将更多专家放到了 GPU；专家张量少 2.73 GiB，不等于 NVML 总显存占用下降 2.73 GiB。

v4-lite 的 2080 已进入全驻留计算图，4080 仍有 420 个专家在 RAM，因此不能称为双卡全部
驻留。测试中 NVML 最低空闲约 **1,131 / 814 MiB**；图捕获日志中的 CUDA 空闲低值约
**786 / 323 MiB**。这两种统计口径不同，不能混用。

初轮沿用 v4 的 1024/128 MiB 预留时，混合版只需 412 MiB RAM 专家，但 4080 的图捕获
日志显示 CUDA 空闲降到 0 MiB。随后将 2080 预留降到 960 MiB，补齐它缺少的 10 个专家；
4080 预留提高到 512 MiB，给计算图留出余量。最终选用这一设置。本轮相对初轮观察到
decode 快约 3%–6%，TTFT 慢约 3%–5%；初轮数据保留在结果文件中。

## 基本能力与长会话检查

原 v2、原 v4、混合版两种预留设置均为 **10/13**。共同未通过库存多步计算、区间合并和
最短路径权重三题；Python 语义、SQL NULL、中文提取、格式化输出和工具参数等检查通过。
题目、预期值和实际回答保留在 [quality.json](../bench/results/2026-10-09-v4-lite/quality.json)。
这是一组关闭 thinking 的小样本，既不能证明混合版强于 v2，也不能证明三者整体质量相同。

所有配置的 32K/128K 输入均取回三个位置的检索串。最终 v4-lite 在长 A → 短 B → 返回 A
时，输入 128,286 token，复用 **128,255**、新读 **31**，TTFT **1.043 s**，三个串再次正确。
300K 是保留的配置容量，本次没有跑到完整 300K 输入。

## 加载实现与校验

本地 pack 为 `pack/iq3kt-v4-lite`，配置为
`strata-iq3kt-v4-lite-k8v8-pf2048-vision-igpu.json`。

- `dense.bin`、`index.txt`、转换记录及 tokenizer 是 v4 的普通复制，逐文件 SHA-256 一致。
- 新 `native_experts.txt` 的每个角色都显式指向 v2 分片，避免空来源默认落到 v4。
  已核对全部 144 项的名称、类型、形状、绝对偏移、载荷和文件范围，引擎加载时再次校验。
- `--native` 和 `--native-head-gguf` 指向 v4；两个 `--native-dense-gguf` 参数分别固定为 v4
  的两个分片；`--ple-gguf` 指向持有 IQ4_KT 大表的 v2 第一分片。
- 显式列出 native dense 分片很必要：引擎的默认逻辑可能把另行指定的 PLE GGUF 加入
  稠密来源。这里分开指定，防止重复或混入 v2 稠密矩阵。

此前已经完整比较了 v2/v4 中的 112 个同格式专家张量及 48 个 router，字节全部相同。
本次复核源文件大小和修改时间后复用该证据，没有重复扫描约 70 GiB 的专家数据。
其余 32 个 gate/up 张量直接使用 v2 的 IQ3_KT 编码，保留发布时的量化结果。

构造方法见 [compose.py](../bench/results/2026-10-09-v4-lite/compose.py)，
来源、哈希及全部专家索引见 [composition.json](../bench/results/2026-10-09-v4-lite/composition.json)。

## 测试条件

同机 RTX 2080 Ti 22 GiB＋RTX 4080 SUPER 32 GiB，i9-12900HK，63.76 GiB RAM，Windows。
同一 `build-kt/pool-candidate/strata.exe`，引擎 0.1.41，SHA-256：

```text
2947bb7c8f50e86cd1ae1b36aedb63527d3802c59800f8b90fc5ac72ef8c52c6
```

共同设置为上下文 307200、YaRN 1.171875、K8V8、resident KV 20480、prefill 2048、
总池 524288、4 个会话名额、12288 MiB 快照预算、prompt-cache 2、固定采样和 GPU 唤醒策略。
没有启用 MTP、suffix draft 或专家动态交换。

初轮混合版与 v2 对照均采用 19＋29 分层和 1024/128 MiB 显存预留，混合版复测改为
960/512 MiB。v2 对照克隆当前 v4 的引擎与运行参数，只换成 v2 权重，避免旧 v2 预设的
不同二进制和缓存设置干扰比较。
原 v4 保持已部署的 22＋26 分层，因此 v4 比较同时包含分层和专家驻留差异。

输入为相同模板、相同 token 序列，greedy、seed 424242、关闭 thinking。每次使用新会话，
核对无前缀复用；固定生成 256 token，排除 warmup。3305/9769 输入各 3 次、32768 输入
2 次、128000 输入 1 次，报告中位数。另测长 A → 短 B → 返回 A，以及 13 项合成基本能力题。

测试程序通过 `Presets` 加锁、识别进程与端口、drain/unload，在 18080 隔离运行；结束后
恢复原启动器 argv/cwd 和 8080 服务。原始配置和日志留在忽略的 `logs/`，不公开其中的密钥。

方法与边界见 [benchmark.py](../bench/results/2026-10-09-v4-lite/benchmark.py)。
基本能力题只用于发现明显退化，不能证明整体质量优于 v2/v4；没有 BF16 参考 NLL/KLD，
未验证完整 300K 输入质量，也没有重做完整 512K 会话池压力测试。

## 本机入口

`run-strata-v4-lite.bat` / `.ps1` 选择新组合，也可执行：

```powershell
.\run-strata.ps1 -Model v4-lite
```

主模型名为 `qwen3.8-flash-next-v4-lite-iq3kt`，沿用当前端口、API key、GPU 唤醒参数及
核显视觉配置。原通用模型名与 v4 模型名作为别名保留。
`run-strata-v4.bat` 和 `run-strata-v2.bat` 仍可切回各自原预设。
启动器和配置由本机的 `strata-models.json` 管理，不提交含凭据的 JSON。

本轮结束时已通过预设管理器切换到 **v4-lite / 8080**。健康检查显示模型已加载、上下文
307200；使用原 v4 模型名的请求返回 `V4_LITE_READY`。原 v2/v4 配置逐文件哈希不变，
实际启动器 argv 只替换配置路径，cwd 和 GPU 唤醒参数已核对。部署证据见
[deployment.json](../bench/results/2026-10-09-v4-lite/deployment.json)。
